# PR レビュースキル（VoiceLab）

## レビューの前提姿勢

- **懐疑的に見る**：動きそうに見えても「実際に動くか」を確認する
- **甘いLGTM禁止**：問題なければ「問題なし・理由：〇〇」と根拠を示す
- **VoiceLab 固有の制約を常に意識する**：Edge Runtime / 音声フロー / TypeScript strict

---

## STEP 1：差分を取得する

```bash
# PR 番号がわかる場合
gh pr diff <PR番号>
gh pr view <PR番号> --json title,body,files,commits

# 現在のブランチの差分を見る場合
git diff main...HEAD
git log main..HEAD --oneline
```

---

## STEP 2：チェックリストで評価する

### 🔴 必須チェック（1つでも NG なら「要修正」）

**機能品質**
- [ ] スタブ・モックではなく実際に動作するコードか
- [ ] API エラー時にユーザーへ日本語でフィードバックしているか
- [ ] エッジケースが処理されているか（空入力・ネットワーク断・長時間無音）
- [ ] `fs`、`path` などの Node.js モジュールを使っていないか（Edge Runtime 制約）

**コード品質**
- [ ] TypeScript strict モードで `any` を使っていないか
- [ ] 環境変数に `process.env.XXX ?? ""` でフォールバックがあるか
- [ ] 新しい純粋関数は `lib/` に切り出してテストがあるか

**テスト**
- [ ] 既存テストが全通過するか（`pnpm test` の結果）
- [ ] 変更した関数に対応するテストが追加されているか

### 🟡 推奨チェック（なければコメントで指摘）

**音声フロー**（音声関連の変更がある場合）
- [ ] Whisper → Claude Haiku → ElevenLabs のパイプラインが維持されているか
- [ ] `MIN_RECORDING_MS = 1500` の制約が守られているか
- [ ] Chrome/Safari/Firefox の音声フォーマット分岐が正しいか

**UI/UX**（フロントエンド変更がある場合）
- [ ] UIに一貫した世界観があるか（白背景・紫グラデーション・量産カードは NG）
- [ ] ローディング・エラー状態が視覚的に伝わるか

---

## STEP 3：レビューレポートを出力する

```
## PR レビュー結果：[✅ LGTM / ⚠️ 軽微な指摘 / ❌ 要修正]

### 概要
（何を変更した PR か・全体の印象）

### ✅ 良い点
- ...

### ❌ 必須修正
- `ファイル名:行番号` — 問題の説明 → 修正方法

### ⚠️ 任意の改善提案
- ...

### テスト確認
- pnpm test：[通過 / 未確認 / 失敗]

### 判定理由
（LGTM の場合：なぜ問題ないと判断したか）
（要修正の場合：何を直せばマージできるか）
```

---

## 判定の基準

| 判定 | 条件 |
|------|------|
| ✅ LGTM | 必須チェックが全通過し、テストも全通過している |
| ⚠️ 軽微な指摘 | 必須チェックは通過しているが、推奨項目に漏れがある |
| ❌ 要修正 | 必須チェックが1つでも NG、またはテストが落ちている |

「たぶん大丈夫」「小さい問題だから」という判断は禁止。
疑わしい場合は「要修正」とし、修正後に再レビューを求める。
